Voice Coding Companion Gap Analysis
Project: /Users/nehadubey/Desktop/voice_agent
Date: 2026-07-05

Goal
Redesign the current voice coding assistant into a more human-like coding companion where:
- Audio/mic is OFF by default.
- Mic starts only from explicit user action: hotkey, mic button, or push-to-talk.
- One user trigger should produce one recording, one backend request, one response, then audio returns to IDLE.
- Highlighted text is only context, never a trigger.
- The assistant can keep task memory active while audio is idle.
- The assistant should not mark tasks resolved unless the user says fixed/done/solved/working or tests/system evidence proves it.

How silence/pause detection is handled today

Silence/VAD is custom RMS logic:

    electron/renderer/renderer.js:408-438

Constants:

    electron/renderer/renderer.js:28-37
    - FOLLOW_UP_WINDOW_MS = 120000
    - RECORDING_MAX_MS = 20000
    - INITIAL_SILENCE_MS = 10000
    - END_SILENCE_MS = 1600
    - MIN_RECORDING_MS = 900
    - SPEECH_RMS_THRESHOLD = 0.01
    - BARGE_IN_RMS_THRESHOLD = 0.045

Logic:
- RMS >= SPEECH_RMS_THRESHOLD sets hasDetectedSpeech = true.
- If speech happened and then quiet for END_SILENCE_MS, stop.
- If no speech for INITIAL_SILENCE_MS, stop.
- If neither happens, max timeout stops at RECORDING_MAX_MS.

Problems:
- This is not robust VAD. Background noise can cross the RMS threshold.
- The backend STT can return fake transcripts for silence, e.g. "... ... ..." or "thank you very much".
- Current code now filters some silence hallucinations, but the architecture still tries to keep the conversation open and can auto-listen.

================================================================================
B. WHAT IS ARCHITECTURALLY WRONG
================================================================================

1. Audio state and assistant mind state are mixed.

Current frontend has:
- conversationActive
- conversationExpiresAt
- autoListenTimer
- sleepUntil

But it does not have:
- audioState: IDLE/LISTENING/RECORDING/PROCESSING/RESPONDING
- assistantMindState: NO_TASK/TASK_ACTIVE/etc.


2. Auto-listening is treated as "human-like".

This causes the exact problem the user does not want. Human-like should mean good memory, tone, and task continuity, not always-on mic.


3. Task memory is too shallow.

Current session memory stores topic and recent turns. It cannot reliably know:
- What bug is active.
- What was tried.
- What the user should try next.
- Whether Neha is waiting for user result.
- Whether the task is resolved.


4. Barge-in violates mic-off default.

Listening during assistant speech means the mic is not off by default.


5. Empty transcript handling is too active.

The frontend retries recording automatically. Desired MVP should not retry without user trigger.

Suggested:

    async function startVoiceFlow(preCapturedContext) {
      if (state.audioState !== AUDIO_STATE.IDLE) return;
      stopCurrentSpeech();
      clearPanels();

================================================================================
I. FINAL DESIRED MVP FLOW
================================================================================

Audio state machine

1. IDLE
   - Mic is off.
   - Assistant task memory may still be TASK_ACTIVE.
   - UI says Ready / Press shortcut.

2. LISTENING
   - User explicitly pressed hotkey/mic/push-to-talk.
   - Capture selected context snapshot.

3. RECORDING
   - MediaRecorder is active.
   - Silence detection only decides when to stop current recording.
   - It never schedules another recording.

4. PROCESSING
   - Audio blob sent to backend.
   - Backend transcribes and runs agent.

5. RESPONDING
   - Neha speaks or displays answer.
   - Mic is off.

6. IDLE
   - Always return here after one response.
   - No auto-listen.


Assistant mind state

1. NO_TASK
   - No active coding task.

2. TASK_ACTIVE
   - A code task exists.
   - Audio can still be IDLE.

3. EXPLAINING
   - Explaining code/task.

4. DEBUGGING
   - Investigating failure.

5. WAITING_FOR_USER_RESULT
   - Neha gave a step and waits for user/test result.

6. SIDE_CONVERSATION
   - Temporary side question.
   - Current task remains in memory.

7. RESOLVED
   - Only explicit user confirmation or tests passing.


Desired interaction flow

1. User highlights code.
2. User presses hotkey or mic button.
3. App captures selected text/context.
4. App records voice once.
5. Backend receives audio + selected code + file context.
6. Backend transcribes.
7. Agent creates/updates current_task.
8. Agent responds in friendly short tone.
9. Agent gives one next useful step.
10. Audio returns to IDLE.
11. Task remains active in backend session memory.
12. Next explicit user message is treated as continuation unless clearly new task.

================================================================================
BOTTOM LINE
================================================================================

The main product mistake is not STT alone. The bigger issue is that the frontend treats "human-like conversation" as "keep listening automatically".

The correct architecture is:
- Audio is explicit, one-shot, and returns to IDLE after every response.
- Task memory is persistent inside the backend session.
- Human-like behavior comes from memory, tone, and task continuity, not from an always-on mic.
